# 枝迹（BranchTrace）— MVP 需求规格（v1.0）

**产品名称：** 枝迹  
**英文名称：** BranchTrace  
**开发代号：** `branchtrace`  
**产品定位：** 以树形项目组织长期目标，以每日行动记录追踪真实推进。  
**界面命名：** 顶部保留 `Project / Daily` 两个主要视图（可分别显示“项目 / 每日”中文标签）；“Todo”仅作为应用类别描述，不再作为产品名称。  
**状态：** 可进入开发；本文件是此前逐项确认需求的统一基线。  
**平台：** Windows / macOS / Linux；离线桌面应用。  
**架构：** Tauri 2 + React + TypeScript + Vite + Tailwind CSS + shadcn/ui + TanStack Query + Rust + rusqlite + SQLite。  
**原则：** 本地 SQLite 为唯一持久化业务数据源；Rust 执行所有业务校验与事务；React 不直接 SQL。  
**词汇：** “项目”= Project 节点；“独立提醒”= Daily-only Reminder；“推进”= 某日确实投入行动的布尔记录，而非进度百分比。

## 1. 产品目标与边界

> 产品命名和工程标识详见 `04_品牌与工程命名规范.md`。该命名变更不影响任何原有业务规则、数据模型和 Tauri Command 的兼容契约。

建立可无限逻辑层级嵌套的长期项目树，同时提供周一至周日的七列 Daily 周视图回顾实际行动和管理日期型待办。Project 管理结构和项目状态；Daily 只读展示 Project 的推进/完成，并直接管理独立提醒。

**首版包含：** Project 项目树、多级子项目、手动排序/跨级移动、按日推进、状态及历史日期、只读 Daily 项目详情、七列周视图、Daily 独立提醒、统一回收站、浅/深/跟随系统主题、本地持久化。  
**首版不包含：** 账号、云同步、搜索、按状态隐藏项目、通知、系统托盘、后台常驻、自动回收站清理、数据导入导出与备份、行动时长/次数统计、项目完成百分比、协作、跨日期拖拽。  
**使用模型：** 单用户、单实例本地数据库；不提供跨进程协同写入保证。

## 2. 全局业务不变量

| ID | 不变量 |
|---|---|
| INV-01 | 所有实体使用不可变 UUID 字符串标识；名称允许完全重复，禁止纯空白，限制 1–500 字符（Unicode 处理以 Rust 为准）。 |
| INV-02 | 业务日期为本地日历日期 `YYYY-MM-DD`（无时区和时刻）；创建/更新时间、完成操作时间、删除时间为 UTC RFC3339 时间戳。 |
| INV-03 | “今天”由 Rust 在执行操作时读取操作系统当前本地日期；不信任前端传入的“今天”。 |
| INV-04 | 一个 Project 每个日期最多一条推进记录；推进与完成互不推导，父子节点互不传播状态或推进。 |
| INV-05 | Project 与 Reminder 各有 `active/completed/canceled` 三态，完成与取消互斥；终止状态只有先恢复 `active` 才能转为另一终止状态。 |
| INV-06 | Project `completed_date` 和 `canceled_date` 不得早于该节点最后一次推进日期；允许同一天推进并完成/取消。 |
| INV-07 | 终止状态的 Project 不能新增推进，但可以删除原有推进记录；恢复后保留所有剩余推进记录。 |
| INV-08 | 删除是软删除；软删除实体不出现在正常视图，恢复不丢失历史；仅明确永久删除会物理清除。 |
| INV-09 | Daily 中的 Project 数据只读；所有 Project 修改只能通过 Project 视图的界面入口完成。 |
| INV-10 | 每次写入由 Rust 在单数据库工作线程内完成最终校验、事务和版本更新。 |

## 3. 导航、启动与全局视觉

- 顶部提供 **Project / Daily** 两个主视图切换按钮；统一回收站与主题设置属于全局入口，不是第三主视图。
- 每次启动进入 **Project**；每次进入 **Daily** 都回到包含当前本地日期的自然周。退出软件后不会保留之前浏览的 Daily 周次。
- 每次从 Project 切回 Daily 以及跨午夜/休眠唤醒/系统时区变化时，重新计算本周、今日、逾期与今日推进状态。
- 每周从**周一**至**周日**；跨月跨年也保持连续七天；上一周、下一周、返回本周。
- Daily 始终是 **七列横向布局**，窄窗口水平滚动；每列建议最小宽度 180–220px，不压缩到不可阅读。
- 主题：`light / dark / system`；默认 `system`，持久化设置，系统主题变化时自动更新（仅 system 模式）。
- 点击窗口关闭按钮**完全退出程序**，无系统托盘/后台常驻；明确处理进行中的写入（完成或回滚）；未提交编辑不保存。macOS 应专门处理默认“关窗不退应用”行为。

## 4. Project 视图

### 4.1 项目树

- 任意层级树形结构；节点 `id` 唯一、`parent_id` 可空（空=顶层），名称允许相同。
- 无搜索框，无状态筛选；正常项目始终可见，只有用户折叠祖先节点或软删除时不可见。
- 展开/折叠状态按节点持久化，切换视图及重启恢复；父项目完成、取消、恢复均不改变展开状态；折叠只改变可见性，不改变后代数据。
- 新项目添加到所属层级末尾；父项目无论 active/completed/canceled 均可创建子项目。若父项目折叠，创建时**临时**展开，创建结束后恢复原状态。
- 支持同级拖拽排序，并保存；**跨级移动只通过“移动到”菜单**完成；目标允许顶层或另一项目，禁止目标为自身、后代、已软删除节点；移动整棵子树，保留状态/推进/展开信息；移到目标层级末尾。
- 从回收站恢复时尽量恢复原位置，若排序位置冲突则采用稳定位置再规范化排序。

### 4.2 创建、编辑与行操作

- 创建采用行内输入框：Enter 提交并继续出现空输入框，Esc 退出；每个 Enter 独立提交，Esc 不回滚先前成功创建的节点。
- 重命名：双击名称或 `··· → 重命名` 进入行内编辑；自动聚焦并选中原内容；Enter 保存，Esc 取消；失败保留草稿并提示。
- 每行直接显示：展开箭头、**只读**状态图标、项目名称、最近 3 个推进日期（如 `#1105 #1106 #1108 +7`）、“今日推进”按钮、`···` 菜单、同级拖拽手柄。
- 状态图标**不可点击**；状态变更统一从菜单发起。菜单包含：标记完成/取消/恢复、修改终止日期、新建子项目、重命名、移动到、移入回收站；菜单按当前状态禁用或隐藏不合法操作。
- 终止状态的今日推进按钮禁用；即使无历史记录也提供日历入口。
- 项目日期摘要选最近 3 个**不同推进日**，按时间升序展示；其余 `+N`；点击日期区或日历按钮打开完整推进日历。日历可跨月浏览，点击合法的今天/历史日期增加或撤销。未来日期不可新增；完成/取消节点只能撤销已有推进记录，不能新增。

### 4.3 Project 状态

| 操作 | 前置条件 | 写入 | 其他影响 |
|---|---|---|---|
| 今日推进开关 | active | 插入/删除当前日记录（唯一约束） | 独立于父子节点、完成状态 |
| 历史推进日历添加 | active 且日期≤今天 | 插入指定日期 | 同一天最多一条 |
| 历史推进日历撤销 | 有该记录，任何状态 | 删除指定日期 | 不触及其他推进记录 |
| 完成 | active | status=completed，completed_date=今天 | 完成不自动生成推进；即刻保存 |
| 取消 | active | status=canceled，canceled_date=今天 | 取消不显示在 Daily；即刻保存 |
| 恢复未完成 | completed 或 canceled | status=active，终止日期清空 | 原 Daily 完成/取消记录失效；推进历史保留 |
| 直接修改完成/取消日期 | 相应终止状态 | 更新对应日期，状态不变 | 日期≤今天且 ≥最后推进日 |

- 无法从 completed 直接改 canceled，亦不能从 canceled 直接改 completed。
- 同级、父子状态完全独立：父项目已终止，子项目仍可新增、推进、完成、取消、移动和编辑；子项目完成不自动完成父项目；父项目完成不自动处理子项目。
- 菜单选择完成/取消**立即用今天写入**，不弹日期选择器；后续可从菜单修改历史日期。
- 成功完成或取消后出现约 **5 秒**“撤销”提示；点击撤销仅当项目的操作版本仍匹配时恢复，避免旧撤销覆盖新修改；提示消失后菜单仍可恢复。
- 校验错误示例：若推进最后日期为 11/08，则终止日期不能设置为 11/07；提示先撤销未来于终止日期的推进记录。校验仅使用节点自身推进，不考察后代。

## 5. Daily 视图

### 5.1 周视图与分组

- 每周 7 列，每日依次三个**顶层分组**：①项目完成；②项目推进；③独立提醒；空分组隐藏。全为空显示简洁空状态。
- `项目完成`：当前有效完成日期是当天的非软删除 Project。若同日也有推进，合并成**一条完成行**，标注“当天也推进过”；数据库中完成字段与推进记录独立。
- `项目推进`：当天存在推进记录，且未在当天完成的 Project；已取消项目过去的推进记录仍保留展示；Project 的取消行为本身**不显示**。
- Project 行只读；点击名称弹只读详情：名称、完整父路径、当前状态、全部推进日期、当前有效终止日期；不得在此编辑或导航到 Project。
- Project 行显示名称和父路径，若可见记录中完整路径同名，额外显示最短足以区分的 ID 前缀（简短 ID 只用于呈现）；路径根据**当前**项目树计算，移动或重命名会改变历史视图中显示的路径。

### 5.2 独立提醒（Daily-only）

- 与 Project 完全隔离；有 `title/scheduled_date/status/completed_date/canceled_date/sort_order` 等字段，**没有** parent_id 或推进记录。
- 每列都有 `+` 新增按钮；仅当天或未来列可用；行内输入，Enter 保存后连续输入，Esc 退出；创建顺序加入计划日期列表末尾。即使跨午夜输入框仍打开，Rust 需按保存时本地日期再次校验。
- 计划日期的新增及**任何状态下直接修改**只能选择今天或未来日期；更改计划日后移到目标计划日期列表末尾，其他日期/状态不变；删除后的恢复不受新建日期限制。
- 未完成提醒使用复选框：点击后**以真实今天**完成，保存 `completed_date` 与 `completed_action_at`；再次点击已完成复选框恢复 active，清空这两个字段。已取消提醒复选框禁用；需先从菜单恢复。
- `···` 菜单：重命名（双击也可进入）、修改计划日期、修改已完成日期、取消、恢复、移入回收站。已完成和已取消状态之间不能直接切换。
- 已完成提醒可以直接修改完成日期为今天或历史日期，状态不变，计划日期保持原样；完成日期可以早于计划日期。直接修改完成日期**保留原** `completed_action_at`；恢复后再次完成生成新操作时间。
- 取消后不进入逾期列表，在计划日期显示“已取消”；恢复时清除取消日期并保留计划日，如计划已过，则重回今日逾期。
- 对于计划日 `D`：始终在 `D` 显示一条计划事项（包括事后已完成/已取消）；对于完成日 `C`：在 `C` 显示完成事项；如果 `D=C`，合并成一条已完成事项；否则是两日各一条展示，底层只有一个提醒实体。
- 对于 `status=active` 且 `scheduled_date < 真实今天` 的提醒：**仅真实今日列**另加一条“逾期待处理”；历史日期不补充逾期列表，原定计划日展示仍保留；原定日等于今天时不重复加逾期。
- 每日独立提醒分组内部：**当天计划**在前、**今日逾期待处理**（仅今天，按最早计划日期优先）居中、**跨日完成**在后；无内容的小组隐藏。
- 当天计划按该日期手动顺序；同一计划/完成日合并提醒保持计划顺序；跨日完成按 `completed_action_at` 由早到晚排序，同刻按 ID 稳定排序。提醒状态变更不调整原计划顺序。
- 仅允许计划日内拖拽手动排序；跨日移动必须使用菜单修改计划日期，不可跨列拖拽。跨日完成副本和今日逾期副本是展示投影，不提供跨日排序拖拽。
- 第一版**没有任何桌面系统通知、定时弹窗、声音提醒或关闭后的通知调度**。

## 6. 统一回收站

- 全局唯一回收站入口，内部切换 `Project 项目` / `独立提醒` 两个分类；分别列出、恢复、永久删除、清空分类。
- 删除 Project 当前节点时，需在确认弹窗显示**当前即将隐藏的活跃节点数**（含自身+活跃后代）。一次软删除生成一个 `trash_entry` 批次，批次内节点统一隐藏；其推进及 UI 状态不删除。
- 若子树中已有**此前单独进入回收站**的后代，则保留该后代原有回收站批次；恢复父项目不会意外恢复先前单独删除的后代。
- 从回收站恢复时，恢复本批次的节点及状态/历史记录，优先原父子关系与位置；若原父节点仍在回收站，必须先恢复父节点。
- 删除 Reminder 时单条入回收站；恢复保留原计划/完成/取消日期和状态，若仍 active 且已逾期就重回今日逾期列表。
- 永不自动清理；永久删除单条/项目树/清空分类必须再次确认。永久删除父树将**连同里面早先单独入回收站的后代**一并物理删除，需按当前总受影响节点数再次提醒。
- 硬删除需要在事务中移除子树、推进记录、UI 状态及关联 trash_entries；不得遗留悬空回收站条目。
- 软删除状态下 Project 和 Daily 均不出现业务记录；恢复时重新显示历史推进及当前有效完成记录。

## 7. 业务时钟与持久化

- 日期解析与比较使用 Rust 日历类型（如 `chrono::NaiveDate`）；日期字段不可存成 UTC 零点时间戳以替代当地业务日。
- 修改系统日期、跨午夜、睡眠唤醒或时区变更后，前端重新请求 Rust 当前日与周数据。过去写入的 `YYYY-MM-DD` 不移动。
- SQLite 保存于系统**应用数据目录**；启动完成版本迁移、外键启用和完整性检测后才显示项目树。异常时显示错误界面，禁止静默新建空库覆盖旧库。
- 单个 rusqlite Connection 归专用数据库线程所有；异步 Tauri Commands 向其发送消息并等待 oneshot 结果；写操作串行化。
- 对业务写操作在事务内执行：检查存在性/未删除/版本/状态/日期/树关系 → 写入 → 增量更新版本 → 提交 → 返回新 DTO；React 成功后使对应 TanStack Query 缓存失效。
- 数据库连接建议 `foreign_keys=ON`、`journal_mode=WAL`、`synchronous=FULL`、`busy_timeout=5000`；设置并检验迁移版本 `PRAGMA user_version`。

## 8. 交互与无障碍默认规则

- 双击重命名之外必须提供菜单入口（支持触屏、键盘）；菜单、日期日历、复选框有键盘可访问状态。
- 拖拽必须由手柄触发，不与复选框、日期区或菜单热区冲突；拖拽排序错误需恢复 UI 原顺序并显示错误。
- 所有数据库变更显示加载/失败状态；失败不可乐观宣称成功；危险操作要求确认；快捷撤销采用版本校验。
- 状态颜色不能是唯一信息来源；应保留图标或文本标签。
- 极窄窗口保留 Daily 七列和横向滚动，超长标题换行或省略并可在详情中完整查看。

## 9. 首版验收测试（必须通过）

1. 同级同名、跨级同名项目可并存；重命名/移动后 ID 和推进历史不变。
2. 父节点完成/取消，子节点仍可操作；子节点完成不自动完成父节点。
3. 当天推进可开关；同日重复不会产生多条数据；第二天今日开关重新未选中但昨日历史存在。
4. 完成/取消后无法新增推进；可以撤销错误的历史推进；恢复后可以重新新增。
5. 完成/取消日期若早于最后推进日期被拒绝；同日可推进并完成。
6. Project 取消当天不展示取消记录，但过去推进仍在 Daily；恢复完成后原完成日在 Daily 消失。
7. 同日推进+完成只显示一条 Project 完成，附推进标记；原始数据未删除。
8. 独立提醒 `计划日=完成日` 只展示一条；不同日各展示计划和完成；历史日期不补充逾期，真实今日显示逾期。
9. 已完成 Reminder 可以修改完成日期至计划日之前；修改计划日只能今天或未来；恢复逾期提醒重新出现在真实今日。
10. 同日计划列表排序持久化；跨日完成列表按照完成操作时间排序；跨日期拖拽拒绝。
11. 删除父项目时整棵活跃子树隐藏；恢复批次保留原状态和历史；独立先删除的后代仍在其原回收站批次。
12. 永久删除后不再能恢复；删除后其他实体不受影响；`PRAGMA foreign_key_check` 无错误。
13. 连续创建 Project/Reminder：Enter 逐条保存，Esc 只取消草稿；窗口关闭后已确认写入存在。
14. 周日跨至周一、跨月和跨年、切换系统时区、睡眠恢复后，本周和今天重新计算，过去业务日不变化。
15. 三平台可启动、离线 CRUD、切主题、正常退出，无数据库写入丢失或阻塞 UI。

## 10. 待开发阶段采用的默认决策（非待确认问题）

- 排序采用同级/同计划日内的整数顺序，复杂调整在事务里规范化到 `1024, 2048, ...`；新建和菜单移动追加到末尾。
- 日期格式错误、非法日期（如 2026-02-30）、空标题、过长标题、目标循环、目标在回收站、过期版本，统一返回可识别的 Rust 业务错误码。
- 软删除批次按删除时间倒序显示；完成操作时间为真实点击完成时刻，不是补记的业务完成日。
- 项目树默认新节点为展开状态；已保存节点的展开状态优先。折叠父节点时创建子项目的临时展开不写入数据库。
- MVP 不自动保存未确认的名称编辑草稿；数据库的日期与状态更新仅在 Rust 成功提交后由前端确认。

## 11. 明确风险及实现说明

1. **软删除批次嵌套：** 先删除子节点、再删除其父节点、再恢复父节点时，原先单独删除的子节点应继续在回收站，不能被父节点恢复隐式复活；永久删除父树时它应一起被实际删除。见 Rust API 事务要求。
2. **结构约束依赖 Rust：** SQLite 自引用外键防止悬空父 ID，但不能单凭普通 CHECK 阻止间接循环；跨级移动必须校验递归后代关系。
3. **日期校验依赖 Rust：** SQL 的文本格式 CHECK 只是基础保护，真实日历合法性、当前日期上限、终止日期约束都必须由 Rust 实施。
4. **本地持久化不等于备份：** 无云同步和第一版导出功能；清除设备数据或磁盘故障仍有丢失风险。首版应至少保证 SQLite 文件与迁移可靠，并为后续备份保留结构化接口。
5. **超深项目树：** UI 和递归 SQL/物理删除需有合理的堆栈与性能保护；不在业务层人为限制常规项目深度，但避免不受控递归和级联删除深度超限。
